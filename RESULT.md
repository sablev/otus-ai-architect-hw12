# Проектирование Data Pipelines и интеграционных шлюзов

Продолжение [архитектуры ДЗ 05](https://github.com/sablev/otus-ai-architect-hw05).
Рекомендации и описания рассчитываются офлайн; LLM размещается согласно
[ADR-009](references/previous-decisions.md#adr-009-размещение-llm).
Обучение, LLM и Qdrant не входят в онлайн-запрос.
Это проект архитектуры; интеграции и производительность не проверялись.

**Схемы:** [приём и очистка данных](https://sablev.github.io/otus-ai-architect-hw12/#/view/index),
[признаки, обучение и онлайн-выдача](https://sablev.github.io/otus-ai-architect-hw12/#/view/features-serving),
[эмбеддинги и предгенерация описаний](https://sablev.github.io/otus-ai-architect-hw12/#/view/embeddings-generation).

## 1. Источники и преобразования

**Клики — поток.** Event Collector проверяет события виджета и сохраняет
событие с outbox одной транзакцией PostgreSQL. Relay передаёт их в RabbitMQ,
consumer сохраняет партиями в S3 и подтверждает обработку. Повторы
устраняются по `event_id`; история позволяет пересчитать данные.

**Каталог — batch.** Суточный XML ERP-каталога поступает через существующий
контур ДЗ 05. ERP — логический источник; место формирования и транспорт
выгрузки уточняются. Прямое подключение к ERP не предполагается.

**Чеки и заказы:** 1С → Bitrix раз в 15 минут → реплика MySQL → адаптер.
Наличие реплики — допущение ДЗ 05. Новый опрос 1С и CDC Bitrix в MVP не входят.

**ELT.** Допустимые исходные поля сохраняются в S3 `raw`, затем Airflow
запускает Python/DuckDB: проверку схемы и SKU, дедупликацию, нормализацию
категорий и единиц измерения, подготовку корзин и оконных агрегатов.
Ошибки изолируются в карантин; неполный снимок не публикуется. Результат —
версионированный Parquet в `curated`. Обновление агрегатов каждые пять
минут — допущение; свежесть ограничена также исходными системами.

## 2. Выбор технологий и полный путь до модели

| Компонент | Выбор и назначение |
|---|---|
| Доставка событий | RabbitMQ: подтверждения и повторная доставка; история — в PostgreSQL/S3. Отдельный Kafka-кластер для MVP не требуется |
| Data Lake | S3-совместимое Object Storage: выгрузки, Parquet, признаки, модели и манифесты. Недорогое хранение и повторный расчёт; совместимость endpoint проверяется на PoC |
| Преобразования | Существующий Airflow + Python/DuckDB: расписание и обработка без распределённого кластера. Spark — при подтверждённой необходимости |
| Feature Store | Feast: определения в Git, offline — DuckDB над S3/Parquet, online — отдельный Redis. Оба контура используют одни и те же рассчитанные значения |
| Прикладные данные | PostgreSQL из ДЗ 05: каталог, идентичность, сегменты, разрешённые исключения, заказы и аналитика эксперимента |
| Векторы и выдача | [Qdrant](https://github.com/qdrant/qdrant#filtering-on-payload) из ДЗ 05: поиск по эмбеддингам с фильтрацией по атрибутам, без новой интеграции. Redis Recommendations Cache — версионированные наборы кандидатов и тексты |

Очищенные корзины → обучение **item-to-item**; обучение LLM не предусмотрено.
Признаки товаров (`category`, `popularity_7d`, `in_stock`) из offline
Feature Store используются для построения и исторической оценки кандидатов,
включая cold start.
Pipeline публикует наборы в кэш; Serving читает их и признаки закреплённого
в релизе снимка из online Feature Store, применяет исключения и правила
ранжирования. Feature Store предотвращает расхождение офлайн-оценки
и онлайн-применения признаков; обучаемого онлайн-ранкера в MVP нет.

Отдельная задача строит эмбеддинги **очищенного каталога** для Qdrant.
Пайплайн кандидатов и Description Generation Worker используют совместимые
эмбеддер и коллекцию. Воркер передаёт LLM атрибуты товаров; Fact Checker
проверяет ответ, publisher сохраняет описание под версией набора.
При отсутствии подходящего текста — шаблон.

## 3. Консистентность и Data Governance

1. **Единые определения.** Код, типы, сущности и окна признаков версионируются
   вместе. Pipeline рассчитывает признаки, Feast хранит и выдаёт их.
   Равенство offline/online-значений проверяется на одних SKU и снимке.
2. **Историческая корректность.** Хранятся `event_time`, `as_of` и
   `available_at` — время доступности по журналу активаций. В историческую
   выборку попадает версия, доступная до момента прогноза. Опоздавшие данные
   и исправления создают новую ревизию с повторной материализацией окна.
3. **Свежесть online.** Serving проверяет версию, отсутствие значений и
   возраст источника. TTL Feast/Redis не заменяет эту проверку. Для остатков
   предлагается предел 30 минут от `source_updated_at`; источник такой
   свежести ещё нужно подтвердить. При неизвестном или просроченном остатке
   товар исключается; при нехватке кандидатов — существующий fallback
   без обещания актуального наличия.
4. **Согласованная публикация.** Манифест связывает версии снимка, признаков,
   модели, эмбеддера, коллекции и набора. Значения изолированы по
   `feature_snapshot_id`. После проверок атомарно меняются указатель релиза
   и журнал активаций; потребители закрепляют версии на время работы.
   Общей транзакции хранилищ нет.
   Предыдущие совместимые артефакты сохраняются для отката.
5. **Идентичность и доступ.** `none`/`session` доступны независимо от связи
   с 1С; `identified` и индивидуальные офлайн-исключения — только после
   подтверждения этой связи. В генеративный контур не передаются ПДн
   и пользовательские идентификаторы. Для сырых данных, карантина и витрин
   назначаются роли доступа, владельцы и сроки хранения.

## 4. Изменения относительно ДЗ 05

Добавлены outbox/RabbitMQ, Data Lake, контур очистки и Feast. Чтение **товарных
признаков** переносится из SQL-витрины в Redis Feature Store; профили,
сегменты и исключения остаются в PostgreSQL. Бюджет ответа p95 200 мс
проверяется нагрузочным тестом с чтением Feature Store. Эксплуатация
дополнительных компонентов в учебном плане закреплена за интегратором.

Перед реализацией нужно подтвердить реплику, источник остатков, сроки
хранения и время обработки снимков. Контракты доставки и публикации —
в [технических примечаниях](DESIGN_NOTES.md).
