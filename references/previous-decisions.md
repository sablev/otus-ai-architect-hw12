# Контекст и предыдущие решения TechnoMart

Унаследованные проектные решения и ограничения ДЗ 05 и 09.

## ДЗ 05: платформа рекомендаций

Источник: [репозиторий ДЗ 05](https://github.com/sablev/otus-ai-architect-hw05).

- Трёхмесячный MVP: сайт, слот `product_card_cross_sell`, A/B-пилот;
  бюджет ответа — 200 мс. Кандидаты рассчитываются офлайн, ранжирование —
  по правилам на запросе, описания генерируются заранее.
- Backend назначает рукав A/B-пилота; Widget передаёт показы и клики
  в Event Collector. События сохраняются в PostgreSQL Raw Event Store.
- Сохраняется обмен 1С → Bitrix раз в 15 минут и суточный XML каталога.
  Чтение реплики MySQL — проектное решение; наличие реплики не подтверждено.
- Агрегированные чеки доступны для обучения item-to-item независимо
  от связи пользователя сайта с клиентом 1С. Персонализация `none`/`session`
  работает без этой связи; `identified` и индивидуальные исключения
  офлайн-покупок требуют её подтверждения.
- PostgreSQL хранит прикладные данные, Redis — кандидатов и описания,
  Qdrant — векторы. LLM и Qdrant не вызываются при онлайн-выдаче.

## ADR-009: размещение LLM

Краткое изложение ADR-009 из ДЗ 09; статус исходного решения —
**Accepted для PoC учебного проекта**, дата — 20.09.2026.

- Для PoC выбрано самостоятельное размещение открытой модели на арендованных
  GPU в российском облаке. Qwen2.5-7B-Instruct на vLLM и одна L4 24 GB —
  стартовая конфигурация эксперимента, без подтверждённого sizing.
- Переход к MVP зависит от проверки качества, производительности, полной
  стоимости относительно SaaS и готовности команды к эксплуатации.
- Модель получает атрибуты каталога без ПДн и идентификаторов покупателей.
  Доступ закрытый, версии весов, промпта и каталога фиксируются.
- При сбое генерации используется шаблон; автоматической отправки каталога
  во внешний SaaS нет. Облако и оператор serving остаются частью модели
  доверия и эксплуатационной ответственности.
