# Технические примечания к ДЗ 12

Контракты доставки, признаков и публикации к [основному описанию](RESULT.md).

## Доставка и повторная обработка

- Event Collector записывает событие и outbox в PostgreSQL одной транзакцией;
  приём подтверждается после commit. Гарантии конвейера начинаются с принятого
  события: `sendBeacon` не гарантирует доставки всех действий пользователя.
- Relay использует persistent messages, durable queue, publisher confirms
  и проверку маршрутизации; сообщение отмечается отправленным только после
  подтверждения. После неоднозначного сбоя оно может быть передано повторно.
- Consumer использует manual ack после записи партии в S3 и checkpoint.
  Идентификатор партии и ключи объектов стабильны при повторе; в `curated`
  дополнительно действует дедупликация по `event_id`. Это at-least-once
  с идемпотентными эффектами, без обещания end-to-end exactly-once.
- Очередь недоступна — события остаются в outbox; S3 недоступен — ack
  откладывается. Контролируются размер outbox, возраст старейшего события,
  очередь и свободное место. При исчерпании места новые события отклоняются
  с сигналом ошибки. Отдельный карантин хранит причину ошибки и ссылку
  на исходную запись; повтор запускается после исправления.
- A/B-поля берутся из назначения Backend, а не из произвольных значений
  клиента. Фолбэк в рукаве treatment не меняет `variant`: сохраняется
  подход intent-to-treat из ДЗ 05.

[Подтверждения RabbitMQ](https://www.rabbitmq.com/docs/confirms) допускают
дубли. Durable queue не заменяет
[репликацию брокера](https://www.rabbitmq.com/docs/reliability).

## Feature Store: время, версии и публикация

Бизнес-сущность — `product_id`, признаки — `category`, `in_stock`,
`popularity_7d`. Для изоляции подготовленных и активных значений составной
Feast entity key — `(product_id, feature_snapshot_id)`. Снимки неизменяемы;
одно поле `feature_version` само по себе не изолирует записи Redis.
`in_stock` поступает только из подтверждённого источника остатков:
клики и чеки не позволяют восстановить его достоверно.

| Поле | Значение |
|---|---|
| `event_time` | Время исходного клика/чека или изменения атрибута |
| `as_of` | Конец окна/момент, на который рассчитан признак |
| `available_at` | Когда конкретное значение стало доступно online-потребителю; фиксируется публикацией, не временем запуска DAG |
| `source_updated_at` | Время последнего подтверждённого обновления источника, необходимое для проверки свежести |
| `feature_version` | Версия схемы и преобразования; несовместимые изменения публикуются отдельно |
| `feature_snapshot_id` | Идентификатор конкретного набора значений; входит в ключ online-хранения и манифест |

Агрегат с `as_of=00:00`, опубликованный в `02:00`, недоступен историческому
запросу в `00:30`. Действовавший `feature_snapshot_id` восстанавливается
по журналу активаций. Исправления не переписывают историю доступности.

Материализатор читает **staged-снимки**, которым ещё не назначен
`available_at`. После активации журнал идемпотентно архивируется в S3;
отдельное **историческое представление** соединяет признаки с этим журналом
и получает фактический `available_at`; неактивированные снимки исключаются.
Историческая выборка строится только до watermark полностью архивированного
журнала; его задержка не должна незаметно исключать опубликованные значения.

[DuckDB offline store](https://docs.feast.dev/reference/offline-stores/duckdb)
поддерживает исторические выборки и материализацию из
[FileSource на S3/Parquet](https://docs.feast.dev/reference/data-sources/file).
[Point-in-time join](https://docs.feast.dev/getting-started/concepts/point-in-time-joins)
использует `timestamp_field="as_of"`; время строки `entity_df` — момент
исторического запроса, ключ снимка — из журнала активаций. В проверенном
[Feast v0.66.0](https://github.com/feast-dev/feast/blob/v0.66.0/sdk/python/feast/feature_store.py)
для этого есть `filter_by_created_timestamp=True`; `created_timestamp_column`
связывается с достоверным `available_at`. Режим включается явно и проверяется
на позднем поступлении данных, в том числе при смене версии Feast.

Расчёт и расписание выполняет Airflow/Python: Feast
[не заменяет ETL и оркестрацию](https://docs.feast.dev/).
Для опоздавших записей со старым `as_of` применяется отдельный backfill
нужного интервала; продвижения incremental watermark недостаточно.

В [Redis backend Feast](https://docs.feast.dev/reference/online-stores/redis)
TTL исторической выборки не гарантирует свежесть online-ответа. Serving
проверяет метаданные каждого обязательного признака; чтение другого
признака или новая материализация не должны «омолаживать» старый остаток.
Учебные пороги свежести: категория и популярность — до 24 часов от `as_of`,
остаток — до 30 минут от `source_updated_at`; требуют согласования.
При недоступности Feature Store применяется fallback ДЗ 05 без чтения S3.

## Согласованный релиз

Манифест в S3 содержит `dataset_snapshot`, `feature_version`,
`feature_snapshot_id`, имя `FeatureService`,
`candidate_model_version`, `embedding_version`, `collection_name`,
`candidate_set_version`, схему нормализации и контрольные суммы артефактов.

1. Подготовить или переиспользовать совместимые неизменяемые версии
   датасета, item-to-item и коллекции эмбеддингов. Обновление признаков
   не требует переобучения модели и перестройки индекса. При смене эмбеддера
   коллекция пересчитывается целиком; удалённые SKU исключаются
   из следующей версии.
2. Материализовать новый `feature_snapshot_id` и подготовить кандидатные
   наборы в Redis, сохранив старые. Проверить parity staged/online-значений
   и метаданные. Пока указатель релиза не изменён, Serving читает старый ключ.
3. Подготовить описания и проверить факты. Отсутствующий или несовместимый
   текст заменяется шаблоном и не блокирует публикацию кандидатов.
4. После проверок одной атомарной операцией в Recommendations Redis сменить
   `active_release` и добавить запись журнала активаций с `published_at`,
   полученным по времени сервера. Этот журнал — постоянные метаданные:
   он защищён от eviction, сохраняется через AOF и архивируется в S3.
   При недоступности записи/восстановления активация блокируется. Serving
   читает указатель один раз на запрос и использует соответствующий ключ
   признаков; воркеры закрепляют манифест на время задания. Отсутствующий
   компонент вызывает fallback, а не смешивание версий.
5. Для отката вернуть указатель на предыдущий манифест и записать активацию
   в журнал. Данные и namespaces сохраняются в пределах окна отката;
   свежесть признаков проверяется повторно.

Alias Qdrant можно переключать атомарно
[внутри Qdrant](https://qdrant.tech/documentation/manage-data/collections/#collection-aliases).
Воркеры используют имя коллекции из закреплённого манифеста: отдельное
переключение alias не должно соединить новый индекс со старым эмбеддером.
Общей транзакции PostgreSQL/S3/Qdrant/Redis не предполагается; согласованность
достигается подготовкой версий, проверками и единой точкой их активации.
Атомарная операция над указателем и журналом — проектная логика publisher,
а не встроенная гарантия Feast. Для неё применимы
[серверные операции Redis](https://redis.io/docs/latest/develop/programmability/eval-intro/);
ошибки и восстановление этой операции должны проверяться при реализации.
